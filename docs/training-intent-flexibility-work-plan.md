# Training intent and flexibility incident remediation

Scope: RF-15/CA-15.2/7/11–13, RF-18/CA-18.1/4/6–8,
EXT-CA-AI-02.27/29/31–33, RN-13/16/29–31, RNF02/05 and pt-BR feedback.
Canonical requirements remain in `docs/requirements.md`.

Read-only account inspection confirmed the reported flexibility request was
prefixed by a copied client role label on its own line. It bypassed direct
generation and reached generic chat with historical mixed-goal context. The
current message actually identifies one goal. The explicit one-day retry entered
generation but its candidate failed completeness. No raw client/health transcript
or account identity is exported here.

Additional confirmed implementation causes: goal recognition uses unbounded
substrings; every retrieval query adds strength-training vocabulary; the owner-RAG
exercise dictionary and constrained writer support only resistance repetitions,
although the domain, database, presentation and frontend already support typed
flexibility holds with side and rest.

Plan:

1. Normalize only bounded copied client-role wrappers, keeping original stored
   messages and UUID replay. Explicit current generation overrides historical
   goals. Preserve negation, conditional requests and non-request discussions.
2. Share token-bounded, accent-insensitive goal recognition and priority/negation
   handling. Ask about priority only for actual positive competing goals; keep
   optional schedule clarification separate.
3. Build goal-specific retrieval vocabulary without injecting resistance terms
   into flexibility requests or borrowing an old goal from onboarding.
4. Add technical flexibility movement identities and reuse existing typed
   flexibility quantities. The writer chooses dose from supplied owner-accepted
   rules; never convert seconds to resistance repetitions or invent measurements.
   Keep final identity/mode/load/side checks, review, citations and atomic saving.
5. Add offline intent, schema, retrieval, chat/replay, rollback and modality
   regressions. Freeze synthetic actual-provider flexibility requests with and
   without copied labels and with optional day schedules; retain every attempt.
6. Run related/full backend checks, review the task diff, update exact technical
   authorization, recreate the local backend and verify read-only readiness.

No new dependency, architecture, professional appraisal, source approval or
automatic activation is introduced. The account's approved plan/history will
not be changed by diagnostics. This is technical verification, not clinical
qualification or an independent evaluation.

All 39 new intent/flexibility regressions passed, and the final full backend
